# Online model and initialization-parameter audit (2026-09-27)

## Scope and evidence

This audit describes the current repository source, not a new performance experiment. It separates the contextual service model, legacy band API, routing heuristics, and cold-start admission. Primary local sources: `include/same/detail/online_model.hpp`, `src/online_model.cpp`, `include/same/resources.hpp`, `src/resources.cpp`, `include/same/config.hpp`, `src/application.cpp`, `docs/contextual-learning.md`, `docs/contextual-model-performance.md`, and `docs/contextual-scan-performance.md`. No user filesystem or production model database was inspected. Existing validation results are cited rather than rerun.

## Mathematical contract

Each content worker owns a separate four-feature model for each of CPU, CUDA, and iGPU. For bytes B, effective batch L, and observed peer count C, x = [1, B/2^20, ceil(B/L)/1024, (B/2^20)C/1024]. The response is successful full-file hash service time in milliseconds, including file reads and device/resource contention, not kernel-only duration or scan makespan. CPU/iGPU C counts host-side CPU+iGPU work; CUDA C counts active CUDA work. Only the selected, successful, unretried backend provides a label. Eligible tasks are profiled; below the 16 MiB default accelerator floor, one in 64 tasks per worker is profiled.

Per backend, S = sum(xx^T), t = sum(xy), q = sum(y^2), W = sum(weights). D_ii = sqrt(max(S_ii, 1e-24)); a Cholesky solve computes (D^-1 S D^-1 + 1e-8 I) theta = D^-1 t and beta = D^-1 theta. First four run observations trigger each-fit updates, then every 16 observations. Prediction is x^T beta if finite and positive, with an in-sample RMS residual and a coordinatewise training-range flag. Invalid numerical state or a failed solve does not publish a new fit. The older 32 factor-four size-band, alpha=1/8 per-byte EWMA API still exists but the current automatic choice calls the contextual overload.

At run startup, matching device/CPU identity plus worker-count history is loaded from `.same/model.db`, multiplied by 0.9 in sufficient-statistic weight, and copied into worker-local models. The raw sample count is not decayed. At successful shutdown the prior is merged only once per identity key, plus each worker's run delta. A new identity starts without synthetic performance priors. No within-run age weighting is present: all accepted observations during one run enter S,t,q with weight one. Thus 0.9 is a per-run forgetting rule, not a five-sample or wall-time half-life.

Important implementation qualification: `save_learning` skips any backend identity with zero new observations in the run. That identity's stored state is not written back, so successive CPU-only runs do **not** compound 0.9 decay on an unused GPU prior. Each later load applies 0.9 afresh to the unchanged stored statistics. The ~6.58-run half-life below applies only to a history key repeatedly saved after new observations; it is not a universal age guarantee for inactive backends.

Routing first applies accelerator size/budget/availability checks. Default `gpu_min_bytes` is 16 MiB; below it the CPU is mandatory. With unknown service models the static preference is CUDA (then iGPU) only from 64 MiB, otherwise CPU. Per-worker size-band first exploration attempts are capped at two per candidate, with periodic deterministic attempts every 64 eligible arrivals. For known in-domain predictions, an accelerator is chosen only if its predicted service plus in-sample RMS is below 0.95 times CPU predicted service minus CPU RMS. This is not a calibrated confidence comparison. Device startup is separately gated by a 100 ms CUDA/iGPU default bootstrap estimate, historical iGPU maximum setup cost when available, or run-local credit equal to 0.05 times completed eligible CPU service divided by worker count minus cold expenses. The gate is best effort, not a hard startup cost bound. With four workers and no other cost or known saving, funding a 100 ms estimate requires about 8,000 ms of cumulative eligible CPU service (100*4/0.05); with eight workers, about 16,000 ms.

## Parameter judgment and limitations

| Parameter | Judgment | Evidence / caveat |
|---|---|---|
| Four-feature linear form | Reasonable low-cost local baseline, not validated as a causal or generally calibrated cost law | Batch count and bytes can be nearly collinear with fixed L; I/O cache state, startup, remaining workload, and interaction effects are unmodeled. Device properties partition state rather than supplying transferable regression features. |
| Normalized ridge 1e-8 | Numerical safeguard, not empirically tuned regularization | Diagonal scaling changes interpretation versus a fixed physical-unit penalty. Existing collinearity test establishes a solvable case, not prediction calibration under sparse/shifted data. |
| First 4 / then every 16 fitting | Sensible bounded CPU overhead, not proven optimal adaptation cadence | Fit can be based on one observation, whose in-sample residual may be near zero. A full run gives equal weight to old and new samples, so a within-run regime shift may adapt slowly regardless of refit cadence. |
| Per-run decay 0.9 | Plausible conservative persistence policy, not evidence-backed optimum | At equal observations per run, old-run weight half-life is ln(0.5)/ln(0.9) ~6.58 runs; many new observations in a single run still receive no within-run forgetting. Scan frequency is not elapsed time. |
| RMS and 5% CPU margin | Useful conservative heuristic but no uncertainty guarantee | RMS is training error; selection-dependent labels and feature-domain checks do not establish out-of-sample error coverage. The margin should be evaluated using held-out/pre-decision errors and end-to-end regret. |
| 16 MiB eligibility / 64 MiB cold preference | Defensible protective starting defaults, not universal crossover sizes | The final local short-workload study showed that default small files avoid discovery; it did not demonstrate acceleration on sustained large jobs. |
| 100 ms setup fallback / 5% credit | Conservative initial admission heuristic, hardware-dependent | A deliberately optimistic 1 ms physical iGPU test measured ~354.620 ms setup; its next process reused the measured setup cost and deferred activation. The default 100 ms is not a safe upper bound or measured device-specific prior. |
| 2 initial attempts / 64 periodic arrivals | Bounds exploration pressure, but proof of adequate coverage is absent | Exploration is worker-local and deterministic, may fragment evidence, and only selected-device outcomes are observed. Cold-start gates can suppress attempted exploration. |

The final local preflight-gated study (Windows/i9-12900H, two warmups and seven measured rounds per condition, 74 correct scans) reported default-floor small median wall times of 104.147 ms for auto+PGO versus 96.225 ms for auto/no-PGO, and mixed 101.664 versus 105.399 ms. Neither automatic condition discovered or initialized iGPU on these short workloads; therefore these measurements support avoiding wasteful startup, not a GPU speedup or parameter optimality. CPU+PGO was 106.571 versus CPU/no-PGO 94.723 ms on small tasks; persistence accounted for several milliseconds. Earlier negative results are preserved in the same report. The hot single-thread model microbenchmark reported ~20.923 ns per contextual prediction and ~116.541 ns per amortized observation, but does not measure full scheduling, contention, or scan speed.

## Selected-feedback starvation (follow-up)

CPU observations never directly update CUDA/iGPU coefficients. The risk is opportunity starvation, not numerical contamination: when a provisional GPU exploration is rejected by cold admission, execution falls back to CPU and no GPU service label is generated. The initial per-band exploration counter increments only after successful backend activation/selection (`src/resources.cpp`, `select_backend`), so a denied GPU attempt remains eligible for a later retry. Periodic exploration every 64 *eligible arrivals per worker and size band* also remains. Neither mechanism guarantees a completed GPU observation: both pass through the same 100 ms or history-based cold gate, and run-local credit resets next process. Below the 16 MiB eligibility floor, GPU observations are intentionally impossible. Thus a series of short scans can retain only CPU labels indefinitely even when a GPU might have been beneficial on some eligible shape; conversely this conservatism can correctly avoid setup costs that exceed remaining work. Which interpretation holds requires a counterfactual experiment, not CPU-only logs.

Reproducible diagnostic: use one controlled eligible size band and `--rehash`, record per-run CPU/CUDA/iGPU accepted samples, exploration selections, deferred CUDA/iGPU counts, cold credit/spend and device setup, and compare default auto with a separate forced-device control on the same bytes and randomized execution order. Verify complete outputs and include startup in wall time. A nonzero number of exploration *decisions* without completed device samples is not evidence that the model has learned the device. Do not add unconditional GPU probing solely to make data symmetric: it may regress short scans. If the controlled long-lived workload shows missed benefit, consider a budgeted, shared, size-stratified completed-probe guarantee rather than merely increasing provisional exploration frequency.

An explicit `same train` command now offers an opt-in way to pay for all three backend labels outside ordinary scans; implementation and bounded physical-device smoke are recorded in [train-mode-validation.md](../train-mode-validation.md). Its existence does not imply that an auto scan should proactively start accelerators, nor that its selected corpus represents a production workload. The single pool-wide iGPU backend described in the following historical audit was later removed; see [per-worker iGPU concurrency](../igpu-worker-concurrency.md) for the new ownership and validation evidence.

## Lazy versus asynchronous activation (follow-up)

These are independent choices. Lazy activation controls **whether/when** the process pays GPU setup; asynchronous activation controls **whether that paid setup overlaps useful CPU/metadata work**. `Resources` is constructed before `scan()`, but `scan()` learns which files actually miss the hash cache at `src/application.cpp` lines 601-623. Therefore unconditional asynchronous setup at resource construction would still charge cache-hit and all-small scans. The original lazy design deliberately avoided that cost; earlier short-scan experiments observed hundreds of milliseconds of wasted iGPU discovery/setup, later preflight gating eliminated it for the final short fixture.

The current first-demand activation is synchronous on the selecting worker, while other workers continue CPU work. CUDA's primary context is process-shared, but worker streams, buffers and backend objects are created and destroyed on their owner threads (`src/resources.cpp`, `prepare_gpu`, `run`; `src/compute_cuda.cu`). OpenCL program/context creation and source compilation are shared and currently synchronous; the single pool iGPU backend has its own admission and handoff invariants (`src/compute_opencl.cpp`, `program_for`; `src/resources.cpp`, `select_igpu`). A background thread may safely prewarm a shared context/program only with explicit publication, error and shutdown contracts; it must not silently move worker-owned CUDA objects or omit correctness validation. CUDA documents primary-context sharing across host threads and runtime initialization on `cudaSetDevice` in CUDA 12+, but not zero setup cost: https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html . Khronos documents that `clBuildProgram` with a null callback waits for compilation, as used here: https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clBuildProgram.html .

Recommended experiment before implementation: compare (A) current first-demand lazy setup, (B) unconditional startup background setup, and (C) budgeted async prewarm triggered by the first eligible cache miss or a bounded backlog. Preserve forced CPU/no-PGO semantics and default output correctness. Measure process wall time, scan/metadata/hash critical path, discovery/setup duration and overlap, driver-induced CPU contention, initialized devices with zero useful hashes, memory, backend work, and failures. Include all-cache-hit, all-small, one-large-file, and sustained-large-file cases. Background launch is beneficial only when saved critical-path latency plus subsequent GPU service savings exceed resource contention and unnecessary setup. Do not hide the setup time by moving it outside the reported scan/process interval.

## Highest-value next experiment

Do not change defaults based on this audit alone. Use a fixed binary and ordinary generated files under repository `.cache` or `.temp`; force rehash, isolate `.same` state per arm, validate complete digests/groups, and interleave randomized order. Stratify payloads (4 KiB, 1 MiB, 16 MiB, 64 MiB, 512 MiB), cache state, worker count, device startup state, and within-run speed drift. Compare current defaults against a small preregistered parameter grid: eligibility 16/64 MiB, startup fallback 100 ms versus measured setup history, decay 0.9 versus a bounded within-run forgetting variant, and RMS margin versus held-out-error-calibrated margin. Record backend choice, setup/discovery costs, pre-update residuals by backend and size, known/out-of-domain rate, PGO lifecycle time, end-to-end wall time, and peak memory. Include forced CPU, static/no-PGO, and forced available devices as controls. A single-machine optimum must not be exported as a universal default. Parameter changes must preserve external CLI/config compatibility.
