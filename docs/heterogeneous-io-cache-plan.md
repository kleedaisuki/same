# iGPU、异步 I/O 与跨运行缓存：研究方案

日期：2026-09-10。状态：**研究与架构决策，不是生产功能已完成的声明**。
代码基线：`a4cacae02c96f50b5d3bdfa51784f1671c1dcc82`；隔离实验提交：`5b7cd90`。

## 0. 问题定义与结论

目标是在不改变 `same` 的文件发现、BLAKE3 摘要、精确比较及失败传播契约的前提下，
降低扫描完成时间。研究对象是本机 Windows/NTFS 与 CPU、Iris Xe、RTX 3070 Ti 的组合；
跨平台保留现有 CPU、CUDA 与普通遍历路径。不把设备利用率最大化当作目标。

**选择的方案：三设备强类型身份 + 工作线程本地模型 + 有界设备准入；元数据批量枚举与
内容异步读取分层；路径/元数据缓存采用独立可失效索引，日志只提供失效证据，不提供快照。**

| 决策 | 采用 | 不采用及原因 |
|---|---|---|
| iGPU 接口 | 可选 OpenCL 原生后端，先保持同步 `Compute` | 不把 Python 原型作为生产运行时；不要求所有用户安装新工具链 |
| 任务调度 | 一个有界 FIFO，固定内容 worker，出队后选择设备 | 不立即拆成三个全局任务队列；避免迁移、饥饿及重复预算 |
| 在线分析 | 明确任务/设备/读取三个计时边界，少量模型状态 | 不用内核时间替代文件服务时间，不把残差当统计置信区间 |
| iGPU 内存 | 纳入主存预算，映射与复制分别测量 | 共享物理内存不等于零复制、零同步或额外免费内存 |
| 常规回退 | 已安全结束的设备失败后整文件 CPU 重试一次 | 不拼接不可信 GPU 中间状态；不吞掉文件变动或校验失败 |
| 驱动挂起 | 停止准入；有硬响应需求时使用隔离辅助进程 | 不以超时为理由释放仍可能被设备访问的缓冲 |
| I/O Ring | 内容读取候选后端，运行时逐操作探测 | 当前公开接口不是 `open/stat/query-directory` 的批处理器 |
| 元数据访问 | 优先量化现有句柄复用，实验批量目录信息与有界元数据工作池 | 不直接读取 NTFS 原始 MFT，不绕过访问控制 |
| 跨运行索引 | 路径绑定、对象版本、扫描证明分离 | 不把路径、File ID 或 size+mtime 单独视作内容版本 |
| 默认一致性 | 保留新鲜枚举、新鲜句柄戳与最终精确比较 | 不因 USN 连续就默认跳过一切枚举和 stat |

三个配套研究记录：[模型](research/igpu-model.md)、[元数据与缓存](research/windows-metadata-cache.md)、
[本地验证](research/local-evidence.md)。既有 [实验记录](igpu-blake3-experiment.md) 保留原始数据和局限。
交付范围、独立评审修订与逐项核验见 [完成审计](research/proposal-audit.md)。

### 2.1 类型比布尔分支更重要

当前 `OnlineModel::predict(bool gpu, ...)`、`Worker::gpu_*` 和 `name()=="cuda"` 都含二元假设。
先引入下列语义，不做“再加一个 is_igpu”的局部补丁：

| 类型 | 语义与约束 |
|---|---|
| `BackendKind` | `cpu / cuda / opencl_igpu`；后端种类，不等于物理设备 |
| `DeviceKey` | 后端 + 适配器身份；缺少可靠身份时只做本轮模型，不复用历史模型 |
| `ExecutionShape` | 实际块大小、读后端、内存传输方式、实现版本；不同形状不能偷偷共用成本 |
| `DeviceHealth` | 不可用、初始化、自检、可用、停止准入、已退役、疑似挂起 |
| `BufferLease` | 容量、所有者、在途读取与计算引用；最后使用完成前不可复用 |
| `RouteDecision` | 候选设备、选择原因、预测、探索标记、资源租约 |
| `Observation` | 实际设备、成功状态、尝试代次、计时边界、形状与争用上下文 |

初版一个 Intel iGPU、一个 CUDA 设备就足够；不引入通用设备插件平台。
初版在文件之间分配设备，不把单个文件的树分给多种设备；避免引入跨设备树状态与重放协议。
保留现有 `Compute` 的同步生命周期与完整 Hasher 行为；跨平台 CPU-only 构建不链接 OpenCL。
OpenCL 头文件/加载器按固定版本与许可证记录管理，运行时设备不存在属于正常可用性结果。
不因检测到 Intel 品牌就断言可用：须确认 GPU 类型、设备能力、内核构建与差分自检。

### 2.2 兼容性

- `--cpu` 不触发任何 GPU 探测；`--cuda` 保留现有 CUDA 尝试及回退语义。
- iGPU 先通过新增显式实验选项启用；未过端到端门槛前不改变默认 `auto`。
- `--no-pgo` 关闭学习，不关闭正确性检查；`--no-telemetry` 不改变调度。
- 旧 `gpu_*` 遥测保持 CUDA 含义，新增按设备维度的数据；不能把旧键悄悄改成 CUDA+iGPU 合计。
- 摘要格式与现有 `state.db` schema v1 不变；新增索引必须可删除、可重建、可被旧版本忽略。

## 3. 数学模型：先分清被预测的量

以任务输入字节数 n、实际块大小 B、设备 d、执行形状 s、争用上下文 z 为变量。
所有时间均以毫秒计，速率以 byte/ms 计，避免 MiB/s 与 byte/s 混用。

同步路径的解释模型：

\[
T_{d}(n,B,z)=T_{open+validate}+T_{read}
+\lceil n/B\rceil L_d+n/r_d+T_{tree+finish}+C_d(z).
\]

这是归因模型，不是假定各项都能独立、无噪声观测。实际在线预测首先学习
**已出队任务的完整服务时间**；冷初始化另记，不反复加到每项预测中。
未来异步流水线允许读取与计算重叠时，不再把两者直接相加；用实际墙钟学习新形状。
稳态理想下界约为 `max(read, compute)`，不是实测必达值。

### 3.1 全局目标不是局部最快

目标是最小化一次扫描的完成时间（makespan），并约束内存、队列、失败率及响应性。
CPU 与 iGPU 共用 DRAM/功耗，因此 `CPU 独跑速率 + iGPU 独跑速率` 不是联合速率。
用流量系数 a 表示每个有效输入字节产生的 DRAM 字节数，有容量边界：

\[
\sum_d a_d X_d + X_{metadata,dram}+X_{other,dram}\le M_{sustainable}.
\]

X 的单位为 byte/s，a 无量纲，M 为持续 DRAM byte/s。磁盘及 CPU 执行能力也有对应约束。
这些是诊断边界，不要求默认运行时读取无法可靠获得的带宽/功耗计数器。

一个**假设反例**：CPU 独跑 20 GiB/s；加 iGPU 后 CPU 降到 12、iGPU 得到 6，合计只有 18。
核显确实在计算，但系统变慢了。必须测联合策略对全轮完成时间的净收益。

### 3.2 简洁的第一版动态分析器

保留每 worker 的后端×32 个四倍大小区间有界模型，区间内记录归一化成本、绝对预测残差和样本数。
成本更新仍可使用指数加权移动平均（exponentially weighted moving average, EWMA）：

\[
u_t=T_t/n_t,\quad c_t=(1-\alpha)c_{t-1}+\alpha u_t,
\quad e_t=(1-\alpha)e_{t-1}+\alpha|u_t-c_{t-1}|.
\]

公式仅用于 n>0 的成功观测；空输入走固定 CPU 路径，不做每字节除法。
保留现有 alpha=1/8 作为起点，而非最优参数。样本形状变更要切换/清空模型代次。
不要为大量交叉特征建立稀疏巨表；先保存争用标签供分析，只有消融证据支持才拆分模型。
上式在粗大小区间会遗漏固定启动成本；首版用核显小块禁用与独立原生校准保护。
只有消融支持才缩窄区间或加入争用模型键；若固定成本残差仍明显，再升级非负截距+斜率
模型，而不是一开始部署通用在线机器学习。

与 CPU 比较时使用保守规则：

\[
\widehat T_d+\lambda E_d+H_d < (1-h)\widehat T_{cpu}-\lambda E_{cpu}.
\]

E 是经验绝对残差，不是置信区间；h 是滞回（hysteresis），H 是需要本次承担的额外成本。
从每字节存储量转换为路由时间时，使用 `T_hat_d=n*c_d`、`E_d=n*e_d`（均为 ms），
不可直接把 ms/byte 的 e 代入上式。H 与已观测服务窗口不得重复计费。
未知模型不代表零时间。**任务已出队，不能再加入同一个 FIFO 的排队等待。**
设备 token 不可立即获得时本项走 CPU，不让所有内容 worker 阻塞在 GPU 准入上。

### 3.3 探索、漂移与全局协调

1. 正确性自检先于性能探索；小文件默认 CPU，iGPU 不因“未知”便获得任意小任务。
2. 初始化由每物理设备一个状态协调；其他 worker 执行 CPU，不重复编译、不永久误判不可用。
3. 一个有界共享探索令牌避免 N 个 worker 同时冷探测；学习仍在 worker 内，不在 FIFO 锁内。
4. GPU 并发额度、探索频率、缓冲上限是资源政策；策略切换只发生在任务边界。
5. 持续大残差、驱动/读后端/内存方式变化触发模型降置信和 CPU 探索；不把温度关联当因果。
6. 仅成功、未回退的观测训练正常服务成本；失败率、重试耗时、丢弃样本单独记账。
7. 不自动加载跨运行性能模型。未来要复用，只能以设备/驱动/内核版本/形状指纹作弱先验，
   并经本轮验证；这与文件元数据缓存是两个独立生命周期。

联合 CPU+iGPU 是否开启不能单凭上述局部不等式。第一版先做受控并发组合实验确定安全
设备配额；运行时保守限制探索和 iGPU 并发。完整混合策略胜过强 CPU 基线才允许默认开启。
若将来在线调节全局额度，按足够长的配对工作窗口评估总吞吐，记录工作集差异，允许回到
已验证基线；不得把不同文件分布的前后吞吐直接称为因果提升。

## 4. 健壮性、回退与生命周期

```text
Unprobed → Initializing → SelfTest → Ready
    failure ─────────────────────► Unavailable (this run)
Ready → returned device error → stop admission → quiescent → Retired → CPU retry once
Ready → digest mismatch ──────► fail scan + rollback; do not publish
Ready → call not returning ───► SuspectedHang; do not reclaim in-flight buffers
```

**返回错误也要检查已有提交的完成状态**，不能假定所有历史命令均已停止。
一般设备错误在确认安全结束后重新打开文件，从零创建 CPU Hasher，重读并复查句柄和路径戳。
一个请求只有一个最终完成通知；尝试代次用于拒绝迟到结果，不迁移中间摘要。
初始化失败、资源不足、执行失败、正确性失败、文件 I/O 失败使用不同错误分类。

故障范围也须显式表达：工作线程私有分配/队列错误只停用该 slot；已确认上下文丢失则
停止同上下文所有 slot 的准入并排空；物理设备丢失影响该适配器全部 slot，不误伤另一块
GPU。无法判定安全范围时不能以“局部可恢复”继续运行，保留失败并停止本轮。

已知错误摘要会污染候选分桶并导致漏报，因此维持当前**校验不一致导致本轮失败**的契约，
回滚当前扫描事务。不能仅重算当前文件后继续相信同设备先前结果。
如果错误在扫描提交后才被发现，应标记已知受影响缓存不可信并要求下一轮重新哈希；
不宣称已经提交事务能被普通 rollback 撤销。生产路径需在提交前完成本轮要求的验证。

`Compute` 同步契约下，应用侧超时不等于取消。Khronos 的 `clFinish` 没有超时参数；
Windows 超时检测与恢复（Timeout Detection and Recovery, TDR）也不是应用响应时限保证。
不修改 TDR 注册表，不通过杀线程或 detach 绕过所有权。[Khronos](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clFinish.html)、
[Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/timeout-detection-and-recovery)

若后续验收要求“驱动调用不返回时主流程仍能继续”，采用每设备辅助进程（helper process），
其自有 staging 缓冲和代次化消息隔离驱动。主进程超时后使用新的 CPU 缓冲，不复用未确认
安全的共享页。终止 helper 不等于全系统驱动恢复，不能承诺抵御 OS 级故障。
首版普通错误回退不需要支付这项进程/IPC 成本；硬超时模式必须另测其开销和清理边界。

### 4.1 统一资源预算

记 H 为主存载荷预算，V 为独显分配预算：

\[
\sum_w H_{cpu,w}+\sum_l H_{read,l}+\sum_d H_{staging,d}
+H_{igpu}+H_{ipc}\le H,\quad \sum_l V_{cuda,l}\le V.
\]

每块实际分配只计一次；iGPU 共享页不是同时拥有两份容量，真正复制的 staging 则另计。
还要有独立的最大文件句柄数、父任务数、在途读请求数、注册缓冲字节及完成记录数限制。
驱动内部开销、OS 缓存和栈不是这些载荷预算可严格约束的 RSS；报告时不可偷换。
初版 iGPU 低并发额度起步，由实验提升；额度耗尽走 CPU，而非额外创建不受限线程。

## 5. I/O Ring 与元数据：不要优化不存在的接口

当前 SDK 和公开文档中，I/O Ring 有 read/write、注册文件/缓冲等接口，
没有对应 `CreateFile`、`stat`、目录枚举及通用 `DeviceIoControl` 的公开 builder。
所以“用 Ring 加速元数据”的现实拆解是：

1. **减少元数据请求数**：复用已有打开句柄；批量读取目录信息；避免重复路径转换。
2. **隐藏独立元数据请求延迟**：继续用有界元数据工作池，而非假装 stat 已被 Ring 异步化。
3. **让内容读取不堵住计算**：另测 Ring/IOCP 读取流水线，让元数据、读取、哈希重叠。
4. **跨运行减少重复发现工作**：使用可失效索引与日志，但严格处理完整性边界。

`FILE_ID_EXTD_DIR_INFO` 可一次返回多项的 ID、时间、大小和属性，值得与当前
`FindFirstFileExW(...LARGE_FETCH)` 比较；目录记录仍不能无条件代替句柄版本校验。
[Microsoft 目录信息](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_extd_dir_info)

生产工程并非一律追求原生异步：libuv 使用线程池处理文件系统操作；其文件系统文档还
记录 Linux 默认 io_uring 路线曾被回退。这是保留简单可测 fallback 的理由，不是 Windows
没有异步 I/O 的证据。[libuv 文件系统](https://docs.libuv.org/en/v1.x/fs.html)、
[线程池](https://docs.libuv.org/en/v1.x/threadpool.html)

### 5.1 有界读取流水线

读取按显式偏移提交，完成可以乱序，送入 BLAKE3 必须按偏移顺序。
每条活动流先从两个槽位实验，不给每个文件分配无界预取缓存。状态为：

`Free → Reading → Ready → Computing → Free`；失败先停止提交、排空/确认取消，再释放槽位。

短读、EOF、文件增长/缩小、提交部分失败、错误完成、重复/迟到完成都必须测试。
Ring 的注册表/文件句柄/缓冲必须比所有引用它们的在途请求活得长。
IOCP 路线在最初打开时选择重叠 I/O 标志；若必须重开，重新验证对象戳，不能把重开成本
漏算。Ring 的句柄要求按其独立文档处理，不从 IOCP 推断。

协调器仍是 Store 唯一写者。完成线程只发布有界结果，不直接执行 SQL。
Ring 不支持、分配失败或性能未胜出时走普通读取；运行中失败须先安全排空，不能在同缓冲
上立即同时开启同步读取。保留 CPU 与 I/O 后端的正交选择，避免九种组合各写一套应用流程。

## 6. 路径与元数据跨运行缓存

### 6.1 三种事实必须分开

- **路径绑定**：某个根内 `(parent, name)` 当前指向哪个文件对象；硬链接是一对多。
- **对象版本**：卷范围内 File ID + 完整 FileStamp + 摘要算法版本；不是永久 File ID。
- **扫描证明**：根身份、递归/忽略策略、journal 身份与游标、缓存代次及完整性状态。

路径保留原有编码和大小写，不统一转小写或 Unicode 归一化。缓存命名策略改变本身要失效。
目录重命名通过父子绑定处理，不能假定每个后代都有自己的 rename 事件；移入目录要重新
枚举子树；未知父节点、硬链接映射不完整或重解析边界变化要保守协调，不猜测路径。

### 6.2 模式与默认值

| 模式 | 可复用什么 | 新鲜检查 | 定位 |
|---|---|---|---|
| 默认 conservative | 已有摘要；索引仅作提示/调度/失效候选 | 保留普通枚举与完整句柄戳 | 不弱化当前正确性 |
| 增量 inventory | 经过连续日志及协调的路径图、脏集合 | 受影响子树重扫；本轮完整清单的新鲜版本检查 | 初期只影子运行，不凭日志无事件跳过生产枚举 |
| 静止/快照 fast path | 在额外一致性前提下复用元数据与摘要 | 验证前提与证明；失效即回退 | 不把日志连续冒充快照 |

完整 journal 连续性是必要条件，不是充分条件：日志会合并修改原因，长期开着的写句柄、
时间更新延迟和边界竞争都可能破坏“没看到事件就没变化”的推论。
不能只读 CLOSE 记录后宣布未改动。默认必须保留当前新鲜检查。
若要真正默认省掉这些 O(N) 检查，必须另行证明不弱于现有语义，而不是靠命名为 fast/strict。

### 6.3 事务与恢复

初版索引使用独立可重建 sidecar，不升级现有摘要库 v1。索引自己的路径/对象/脏集合与
日志游标放同一 SQLite 事务；**不能声称 sidecar 与 state.db 两个独立提交天然原子**。

跨库完成标记只用于诊断和发现已知不一致，不赋予 sidecar 权威：

| 阶段 | 持久化动作 | 崩溃/提交结果不明后的处理 |
|---|---|---|
| 准备 | sidecar 标记 Building；增量 dirty+cursor 同事务提交 | 下轮重协调，不能把 Building 当完整清单 |
| 扫描 | 按完整新鲜清单执行 v1 Store 的全扫描事务并提交 | 旧摘要库可能已提交；sidecar 未完成不影响下轮普通扫描 |
| 记录完成 | sidecar 保存完成标记与观察到的 scan generation | 标记缺失/代次不符则 NeedsReconcile；标记一致也不取代日志和新鲜检查 |

旧二进制不会更新 sidecar，不能声称总能检测到它运行过；**不依赖检测旧版本运行来保证
正确性**。每轮仍验证根/策略与日志并重新协调，默认始终完整新鲜枚举。备份恢复、根换绑、
缺口和无法证明的状态一致性一律退回协调；state.db 的新鲜戳验证独立保持。

S7 选定的最小方案是：在明确静止树/快照前提下，sidecar 的对象、链接、dirty、游标、
根/策略及发布代次位于同一原子事务域，协调后才提供**完整清单**；所有清单成员仍进行
新鲜戳检查并进入原有 Store 流程。state.db 仍为可重新验证的摘要缓存，不需要新增第三个
同时拥有两种缓存的数据库。跨库崩溃只导致重做，不允许导致路径遗漏。
进一步省掉逐成员元数据查询必须绑定不可变快照身份或另证版本协议，不能通过合并数据库
冒充一致性证明；这是更强的可选快路。没有这一前提时保留默认行为。

每次启动探测 journal ID、有效起点、保存游标是否仍在范围内；缺口、删除重建、卷替换、
未知记录格式、权限不足或过量重放都触发有界失效和全扫，不创建/扩大/重置用户卷日志。
日志读取范围是卷级，开销可能超过一个小根的全扫；必须有字节/时间预算和成本回退。
非特权日志能力单独探测；能读取不代表能得到完整名称或可恢复整个目录树。

### 6.4 为什么最后比较不能修复错误缓存

陈旧摘要可能把真正重复的文件分入不同桶，陈旧路径图可能漏掉新文件；这些是假阴性
（false negative），最后逐字节比较永远碰不到它们。
因此分别验收：**已输出的相等关系可靠**、**输入清单及重复组发现完整**。
当前前后戳检查也不提供线性一致性（linearizability）；严格时间点语义需要静止数据或快照。

## 7. 可执行实施顺序与验收门槛

下表是未来实施计划，不表示本轮已执行这些生产改造。

| 步骤 / 建议提交主题 | 写入区域 | 产物与验收 | 失败时行为 |
|---|---|---|---|
| S0 `test(acceleration)` | tools、benchmarks、研究文档 | 固定实验、原始结果、能力证据；本轮已完成 | 不触碰生产 |
| S1 `refactor(compute): type device identity` | compute/resources/model/telemetry | CPU/CUDA 回归、旧配置与遥测兼容、一次发布/预算测试 | 保留旧路由默认 |
| S2 `feat(igpu): add validated synchronous backend` | 新后端/CMake/compute tests | 官方向量、任意长度、随机分片、故障注入、CPU-only 构建 | 自检失败不得发布摘要 |
| S3 `feat(dispatch): add bounded heterogeneous analysis` | resources/model/telemetry | 同预算三设备与组合试验，漂移/探索/争用消融 | 未胜出则 iGPU 显式 opt-in |
| S4 `perf(walk): batch directory metadata` | walk/files/Windows metadata tests | 与现有清单、戳及拒绝重解析行为差分；真实 syscall/墙钟收益 | 原游标回退 |
| S5 `feat(io): add bounded ring read pipeline` | 新 read stream/lease + application adapter | sync/IOCP/Ring 对照，乱序/短读/取消/文件变化/预算测试 | 安全排空后普通读取 |
| S6 `feat(cache): add advisory inventory` | 新 sidecar/USN parser/policy identity | crash points、日志缺口、重命名、硬链接、忽略变更；影子比对 | 全扫，不误认缓存完整 |
| S7 `perf(cache): enable proven incremental inventory` | inventory application integration | 静止树/快照前提明确；协议审计与变更轨迹差分、清单零遗漏、收益达标 | 无前提或无证明就不启用快路 |

S2 与 S4 在 S1 接口稳定后可由不同 worker 并行；S3、S5 分别通过后才测组合。
S6 不依赖 GPU 实现，可以独立推进。每个文件区域单写者，无需锁整个仓库。
每个提交必须记录构建/测试/已知限制；不把实验、无关格式化与生产特性混在同一提交。

### 7.1 数值性能门槛（提议，尚未通过）

- 正确性为硬门：在支持语义内清单与分组差分零遗漏/零错误，失败不报成功。
- 目标负载端到端中位数至少改善 10%，配对 95% 重采样时间比区间上界 <1；保护负载的
  中位回归不得超过 max(3%, 预先声明的实测噪声容许界)。实质尾延迟退化须否决或独立复审，
  不能靠中位数掩盖。阈值是初始工程政策，不是统计定理。
- 报告 p95、初始化时间、峰值载荷/句柄/注册页、重试时间和故障计数；不能只报均值。
- 小文件/空运行上分析器额外开销目标不超过 1%；热路径默认不逐块写遥测。
- GPU 混合对照必须与 CPU 多核、当前 auto、优化 CUDA 等预算比较，而非只与单线程比。
- 真实文件矩阵覆盖：小文件多、大文件少、深目录、冷热缓存、低/高变化率、外部卷日志
  高写入、插电/电池、前台图形负载；不能把整个矩阵平均值掩盖单个严重回归。
- 读 Ring 和缓存收益分别做消融（ablation），最后才报告组合收益；统计单位是完整一轮，
  不把同一轮内相关文件当成大量独立样本。

### 7.2 故障与兼容性矩阵

必须覆盖：OpenCL 缺失/编译失败/分配失败/中途错误/错误摘要/未返回调用；文件短读与变化；
Ring 不支持操作、提交部分成功、缓冲注册失败、乱序完成、取消竞争；数据库提交前后崩溃；
journal 回卷与 ID 改变；非特权/权限变化；目录改名移入移出；硬链接增删；大小写敏感目录；
根路径换绑；忽略内容/语义/递归开关改变；老版本读写 v1 状态；CPU-only 非 Windows 构建。

## 8. 本轮完成判据

研究交付完成不等于 S1–S7 功能完成。本轮需提供：

1. 代码与本机能力证据；不依赖旧文档推断当前实现。
2. 有变量、单位、目标、样本边界与适用条件的数学模型及动态分析器方案。
3. 明确普通失败/错误摘要/挂起三类故障的回退与所有权契约。
4. I/O Ring 元数据能力边界及可行替代路径。
5. 跨运行缓存的数据模型、失效、事务恢复、权限与一致性边界。
6. 工程与学术来源、竞争方案、实施分解、验收与回退门槛。
7. 独立评审、问题修订和逐项完成审计；未测性能不得标为已实现收益。
